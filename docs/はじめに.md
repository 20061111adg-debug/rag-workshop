# はじめに読む — RAGとは何か

このリポジトリの入口です。**専門用語を使わずに**、RAGが何をしているかを説明します。
`README.md` は詳細版なので、まずこちらを読んでください。

---

## 1. RAGは「カンニングペーパーを渡す仕組み」

ChatGPTのようなAIは、自社の社内規程を知りません。学習していないからです。
だから「うちの在宅勤務手当はいくら？」と聞いても答えられません。

ここで考えられる方法は2つあります。

**方法A：AIに社内規程を覚えさせる**
→ 専門知識と費用が必要で、規程が変わるたびにやり直し。現実的ではない。

**方法B：質問するとき、関係ありそうな部分を一緒に渡す**
→ **これがRAGです。**

つまりRAGは、
**質問に関係ありそうな文書を自動で探してきて、質問と一緒にAIに渡す仕組み**です。

AIから見れば「参考資料を添えて質問された」だけ。特別なことは何もしていません。

---

## 2. いちばん大事なこと：AIは検索していない

ここだけは押さえてください。**多くの人が誤解しているポイント**です。

よくある誤解はこうです。

> ❌ AIが社内文書を検索しに行って、探して答える

実際はこうです。

```
  質問「在宅勤務の手当は？」
        │
        ▼
  ① 普通のプログラムが文書を探す     ← AIは全く関わっていない
        │
        ▼
  ② 見つけた文章を質問の上にコピペする
        │
        ▼
  ③ AIに渡す（1回だけ）             ← AIの出番はここだけ
        │
        ▼
  「月額5,000円です[1]」
```

**AIは①も②もやっていません。**
探すのは普通のプログラム（このリポジトリの `ragkit/` がそれ）で、
AIは最後に渡された文章を読んで、言葉を整えているだけです。

### なぜこれが重要か

**探す段階で見つけられなかった文書は、AIがどれだけ賢くても絶対に答えに出てきません。**
存在すら知らないからです。

だからRAGを良くしたいときは、AIを高性能なものに変えるより、
**探し方を改善するほうがずっと効きます。** 実際このリポジトリでも、
一番効果があったのは「文書の区切り方を変える」ことでした（後述）。

---

## 3. 使われている技術は 6 つだけ

図書館で「書類棚を作って、そこから探す」のに似ています。
**準備が 3 つ、質問が来てから 3 つ**です。

```
【準備】 規程 → ①切る → ②数字にする → ③しまう
                                          ↓
【質問】 質問 → ④探す → ⑤順番を決める → ⑥AIに渡す → 回答
```

準備の 3 つは、**質問が来る前に 1 回やっておくだけ**です。

---

### 準備すること

#### ① 切る 〈チャンク分割〉

分厚い規程を丸ごとは渡せないので、**紙切れに小分け**します。

紙切れは後で**1枚だけ取り出して読まれます**。
なので「どこで切るか」で、その紙切れが意味の通るものになるかどうかが決まります。

```
✗ 決まった文字数で切る
   「…離席についてSlackに投稿すること。
    6. 通信費および設備の補助
    在宅勤務手当として月額5,000円を支給する。…
    7. 執務環境の要件
    自宅以外（カフェ等）で業務を行う場合は…」
                        ↑ 前の話の途中で始まり、次の話の途中で終わる
```

```
✓ 見出しごとに切り、見出しを頭に付ける
   「リモートワーク規程 ＞ 6. 通信費および設備の補助
    在宅勤務手当として月額5,000円を支給する。…」
     ↑ この1行があるだけで、何の話か分かる
```

切り方には、決まった文字数で切る・文の区切りで切る・見出しで切る、などの選択肢があります。

#### ② 数字にする 〈埋め込み〉

紙切れ1枚ずつを、**数字の列に変換**します。

```
  「在宅勤務手当は月額5,000円」  →  [0.21, -0.05, 0.88, … ]
  「家で働くとお金はもらえる？」  →  [0.19, -0.03, 0.85, … ]   ← 近い
  「新幹線のグリーン車の条件」    →  [-0.7,  0.44, 0.02, … ]   ← 遠い
```

**意味が近い文章は、近い数字になる**よう作られたモデルを使います。
これで「言葉は違うが意味は近い」を機械が比べられるようになります。

#### ③ しまう 〈索引〉

変換した数字を**まとめて棚にしまいます**。これで探せる状態になります。

文書が数十万件を超えると、探す速さのために特別な棚の作り方（ANN）が使われます。
それ以下の規模なら、単純に全部並べて順番に比べるだけでも間に合います。

---

### 質問が来てから

#### ④ 探す

探し方は **2 通り**あり、**得意分野が逆**です。

| やり方 | 得意 | 苦手 |
|---|---|---|
| **同じ言葉が書いてある紙を探す**〈BM25〉 | `VaultTeam` のような固有名詞・型番 | 言い換え |
| **意味が近い紙を探す**〈ベクトル検索〉 | 「家で働く」で「在宅勤務」が見つかる | 知らない固有名詞 |

どちらも一長一短なので、**両方やることが多い**です。

#### ⑤ 順番を決める

両方で探すと結果が2つ出てくるので、**1つのリストにまとめます**〈融合〉。

さらに、上位の紙だけを**もう一度じっくり見比べて並べ直す**こともあります〈リランク〉。
丁寧に見る分、時間がかかります。

#### ⑥ AI に渡す

上位の紙を数枚選び、質問と一緒にAIに渡します。**ここで初めてAIが登場**します。

あわせて「**書いてなければ書いてないと答えて**」という指示も渡します。
AIは知らないことをもっともらしく作ってしまうので、その予防です。

---

`README.md` には専門用語が多く出てきますが、**まずはこの3つだけで足ります。**

| 出てくる名前 | ①〜⑥のどれか |
|---|---|
| **BM25** | ④の「同じ言葉を探す」やり方の名前 |
| **埋め込み / ベクトル** | ②の「数字にする」こと |
| **リランク** | ⑤の「もう一度見比べて並べ直す」こと |

残りは、出てきたときに次の用語集を引けば十分です。



## 4. 用語集

説明なしに使われがちな言葉をまとめます。

| 言葉 | やさしく言うと |
|---|---|
| **RAG** | 質問に関係ある文書を探してきて、AIに一緒に渡す仕組み |
| **チャンク** | 小分けにした文書の1枚。「紙切れ」だと思えばよい |
| **チャンク分割** | 文書をどこで切るか。**精度への影響が一番大きい** |
| **埋め込み / ベクトル** | 文章を数字の列に変換したもの。意味が近い文章は数字も近くなる |
| **ベクトル検索** | その数字の近さで探すこと。＝「意味で探す」 |
| **BM25** | 言葉の一致で探す昔ながらの方法。固有名詞に強い |
| **ハイブリッド検索** | 上の2つを両方使って結果を混ぜること |
| **リランク** | 探した候補をもう一度じっくり見比べて、順番を付け直すこと。精度は上がるが遅い |
| **評価セット** | 「この質問の答えはここに書いてある」という正解表。精度を数字で測るために使う |
| **ハルシネーション** | AIが知らないことをもっともらしく作ってしまう現象 |

### README に出てくる、もう少し細かい言葉

`README.md` や `steps/` の中で使っている言葉です。**発表では使わなくて構いません。**

| 言葉 | やさしく言うと |
|---|---|
| **RRF**（逆順位融合） | 2つの検索結果を「順位だけ」で合体させる方法。点数の単位が違っても混ぜられる。「両方が上位に挙げたもの」が勝つ＝多数決に近い |
| **MMR** | 似たような紙ばかり選ばないようにする工夫。「関連度」と「内容の被らなさ」のバランスを取る |
| **バイエンコーダ** | 質問と文書を**別々に**数字へ変換する方式。文書側を先に計算しておけるので速い。ふだんの検索はこれ |
| **クロスエンコーダ** | 質問と文書を**つなげて1本**にしてから判定する方式。精度は高いが毎回計算が要るので遅い。並べ替え（リランク）に使う |
| **TF-IDF** | 「その文書によく出て、他の文書にはあまり出ない言葉」を重視する古典的な方法 |
| **IDF** | 上の「他の文書にはあまり出ない」の部分。珍しい言葉ほど重く扱う仕組み |
| **転置索引** | 「この言葉はどの文書に出るか」の逆引き表。全文書を調べずに済ませるための索引 |
| **LSA / SVD** | TF-IDF を圧縮して、擬似的に「意味」を持たせる古い手法。今回は比較用に実装した |
| **E5** | 今回使った埋め込みモデルの名前（`multilingual-e5-small`）。100言語対応で470MB |
| **cosine（コサイン類似度）** | 2つの数字の列がどれくらい同じ向きかを測る計算。「意味の近さ」の正体 |
| **オーバーラップ** | チャンクを少し重ねて切ること。境界で文が分断されるのを防ぐ狙い。今回は**効かなかった** |
| **top-k / candidate_k** | 上位何件を取るか。`candidate_k` は並べ替えに渡す候補の件数 |
| **ANN / HNSW** | 文書が数十万件を超えたときに使う高速な探し方。今回の規模では不要だった |
| **HyDE** | 質問から仮の答えを作ってから探す手法。今回は未実装（次の改善候補） |
| **信頼区間** | 「この差は本物か、たまたまか」を確かめるための幅。幅が 0 をまたぐなら「差があるとは言えない」 |

### 数字の見方

`README.md` には `MRR 0.927` のような数字が出てきます。ざっくりこう読んでください。

| 数字 | 意味 | 読み方 |
|---|---|---|
| **MRR** | 正解が何番目に出たか | **1.0に近いほど「1位に出せている」** |
| **Recall@5** | 上位5件に正解が入っていた割合 | **1.0に近いほど「取りこぼしていない」** |
| **Precision@5** | 上位5件のうち何割が当たりか | 高いほど「余計なものが混ざっていない」 |
| **nDCG@5** | 正解を上位に寄せられたか | Recall より厳しい。順位の良し悪しまで見る |

MRR と Recall の2つだけ覚えれば十分です。**どちらも 1.0 が満点。**

どちらも**1.0が満点**。それだけ分かれば読めます。

## 5. コードはどこを見ればいいか

2,300行ありますが、**全部読む必要はありません。** 3か所だけで十分です。

| 見る順 | ファイル | 何が分かるか | 行数 |
|---|---|---|---|
| 1 | `steps/step1_naive_rag.py` | **RAGの全工程**が1ファイルに入っている。まずこれ | 135行 |
| 2 | `ragkit/store.py` | 「意味で探す」の正体。実は数字の掛け算だけ | 30行 |
| 3 | `ragkit/generator.py` の `build_prompt` | **AIに実際に渡している文章**。上の③そのもの | 20行 |

残りは、この3つを組み合わせたり、精度を測ったりしているだけです。

## 6. 今回わかったこと（3つだけ）

細かい数字は `README.md` にありますが、**覚えておくべきはこの3つ**です。

ここからは、**実際に測って比べた結果**の話です。
41問の質問と「正解がどこに書いてあるか」の表を用意し、やり方を変えながら点数を測りました。

### ① いちばん効いたのは、第3章①の「切り方」だった

4通りの切り方を試して比べたところ、**見出しごとに切って、見出しを頭に付ける**やり方が最も良く、
素朴なやり方（決まった文字数で切る）との差が最も大きくなりました。

AIのモデルは一度も変えていません。
「高いAIを使えば良くなる」ではなく、**地味な前処理が効く**というのが実感です。

### ② 探せなかったものは、AIには救えない

AIは渡された紙しか読めません。探す段階が全体の上限を決めます。

### ③ 「良くなった気がする」は当てにならない

途中で、**正解表のほうが2か所間違っていました。**
そのせいで「この問題は検索では解決できない」という**間違った結論**を出していて、
直したら結論がひっくり返りました。

測る物差しが狂っていると、**間違った結論に自信を持ってしまいます。**
これが一番怖い、というのが今回の学びです。
